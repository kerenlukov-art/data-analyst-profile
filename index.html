01 · ONBOARDING

ניתוח משפך המרה - מבקרים חדשים (Onboarding)

Funnel AnalysisBigQueryReal data

האתגר העסקי:
מיפוי שלבי מסע המשתמש עבור משתמשים חדשים.
צוות המוצר רצה להבין באיזה שלב במשפך ההמרה משתמשים חדשים נושרים, בין הרגע שבו הם נכנסים לאתר בפעם הראשונה (אירוע first_visit) ועד להשלמת הרכישה, במהלך ה-session הראשון שלהם באתר.

מטרת הניתוח:
אופטימיזציה של משפך ההמרה למשתמשים חדשים.
זיהוי השלב בעל שיעור ה-Drop-off הגבוה ביותר במשפך ההמרה (Funnel Analysis), כדי לגבש המלצות לשיפורי UX ולבחון גרסאות חלופיות (A/B Testing). 

-- 5-stage onboarding funnel:
-- First visit → Viewed product → Added to cart → Began checkout → Purchased
-- Defined within the visitor's first session only (ga_session_id from event_params)
WITH events AS (
  SELECT
    user_pseudo_id,
    event_name,
    event_timestamp,
    (SELECT ep.value.int_value FROM UNNEST(event_params) ep WHERE ep.key = 'ga_session_id') AS session_id
  FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
),

first_visit_session AS (
  -- ה-session שבו קרה ה-first_visit הראשון של כל משתמש (מבקר "חדש")
  SELECT user_pseudo_id, session_id AS onboarding_session_id, event_timestamp AS first_visit_ts
  FROM events
  WHERE event_name = 'first_visit'
  QUALIFY ROW_NUMBER() OVER (PARTITION BY user_pseudo_id ORDER BY event_timestamp) = 1
),

session_events AS (
  -- מצמצמים לאירועים שקרו באותו session בלבד - לא בביקורים חוזרים
  SELECT f.user_pseudo_id, e.event_name, e.event_timestamp
  FROM events e
  JOIN first_visit_session f
    ON e.user_pseudo_id = f.user_pseudo_id
   AND e.session_id = f.onboarding_session_id
),

funnel AS (
  -- פותחים כל שלב לעמודה נפרדת עבור כל מבקר (pivot ידני)
  SELECT
    user_pseudo_id,
    MAX(IF(event_name = 'first_visit',    event_timestamp, NULL)) AS visit_ts,
    MAX(IF(event_name = 'view_item',      event_timestamp, NULL)) AS view_item_ts,
    MAX(IF(event_name = 'add_to_cart',    event_timestamp, NULL)) AS add_to_cart_ts,
    MAX(IF(event_name = 'begin_checkout', event_timestamp, NULL)) AS checkout_ts,
    MAX(IF(event_name = 'purchase',       event_timestamp, NULL)) AS purchase_ts
  FROM session_events
  GROUP BY user_pseudo_id
)

-- ספירת מבקרים בכל שלב + שיעור המרה מצטבר (מסך המבקרים) ומשלב לשלב (מהשלב הקודם)
SELECT
  COUNT(*)                                  AS new_visitors,
  COUNTIF(view_item_ts    IS NOT NULL)      AS viewed_product,
  COUNTIF(add_to_cart_ts  IS NOT NULL)      AS added_to_cart,
  COUNTIF(checkout_ts     IS NOT NULL)      AS began_checkout,
  COUNTIF(purchase_ts     IS NOT NULL)      AS purchased,

  -- % מהשלב הקודם במשפך
  ROUND(SAFE_DIVIDE(COUNTIF(view_item_ts   IS NOT NULL), COUNT(*)), 3)                                     AS view_item_pct_of_prev,
  ROUND(SAFE_DIVIDE(COUNTIF(add_to_cart_ts IS NOT NULL), COUNTIF(view_item_ts   IS NOT NULL)), 3)          AS add_to_cart_pct_of_prev,
  ROUND(SAFE_DIVIDE(COUNTIF(checkout_ts    IS NOT NULL), COUNTIF(add_to_cart_ts IS NOT NULL)), 3)          AS checkout_pct_of_prev,
  ROUND(SAFE_DIVIDE(COUNTIF(purchase_ts    IS NOT NULL), COUNTIF(checkout_ts    IS NOT NULL)), 3)          AS purchase_pct_of_prev,

  ROUND(SAFE_DIVIDE(COUNTIF(purchase_ts IS NOT NULL), COUNT(*)), 3) AS overall_conversion_rate
FROM funnel;

איך המדד חושב

מבקר "חדש" מזוהה לפי אירוע ה-first_visit הראשון שלו בלוג (QUALIFY + ROW_NUMBER), כדי שרישום כפול לא ינפח את האוכלוסייה.

ה-session מזוהה מתוך event_params.ga_session_id, והמשפך מצומצם לאירועים שקרו באותו session של ה-first_visit - כלומר, מה שקורה בביקור הראשון בפועל, לא בכל היסטוריית המשתמש.

שיעור ההמרה בין שלבים = מבקרים בשלב N חלקי מבקרים בשלב N-1. שיעור ההמרה הכולל נמדד ביחס למספר המבקרים החדשים.

הנחות עבודה

  • הניתוח מבוסס על נתוני GA4 Export האמיתי של Google Merchandise Store
    (נוב 2020–ינו 2021), 257,314 מבקרים חדשים בסה"כ.
  • המשפך מוגבל לאותו session בלבד - ביקורים חוזרים של אותו משתמש לא נכללים
  • נבדקו גם פילוחים לפי מכשיר (desktop/mobile/tablet) וערוץ תנועה - שיעור הנשירה בשלב הראשון אחיד (~19.5%–19.9%) בכל הפילוחים, כלומר הבעיה אינה קהל ספציפי אלא חוויית עמוד הנחיתה עצמה

מסקנה עסקית

הנשירה הגדולה ביותר (80.2%) מתרחשת בין הביקור הראשון לבין הצפייה הראשונה במוצר - לא בהמשך המשפך. ברגע שמבקר מגיע לעגלה, שיעור תחילת ה-Checkout גבוה יחסית (67.3%) - כלומר הבעיה המרכזית היא בחשיפה למוצרים, לא בתהליך התשלום.

המלצה

למקד שיפורי UX בעמוד הנחיתה של מבקרים חדשים - למשל קרוסלת מוצרים מומלצים ישירות בעמוד הנחיתה - כדי לקצר את הדרך לצפייה ראשונה במוצר. ראו את מקרה הבוחן הבא (A/B Test) לבדיקת ההשערה הזו.

02 · EXPERIMENTATION

A/B Test - קרוסלת מוצרים בעמוד הנחיתה של מבקרים חדשים

A/B TestingBigQueryControl Group - Real data, Treatment Group - Simulated data

האתגר העסקי:
אופטימיזציה של שיעור ההמרה (Conversion Rate) בשלב החשיפה למוצר.
ניתוח משפך ה-Onboarding הראה כי צוואר הבקבוק המרכזי מתרחש כבר בשלב הראשוני:
80.2% מהמבקרים החדשים נושרים בין הנחיתה באתר לבין צפייה בדף מוצר (view_item).

מטרת הניתוח:
לבחון האם אלמנט UX חדש: קרוסלת "מוצרים מומלצים" , יגרום להעלאת ה-Conversion Rate
וצמצום שיעור ה-Drop-off בשלב החשיפה למוצר.

ההשערה הנבדקת (Hypothesis):
שילוב קרוסלת "מוצרים מומלצים" ישירות בעמוד הנחיתה של מבקרים חדשים יקצר את מסע המשתמש
(User Journey), יפחית חיכוך (Friction) ויגדיל באופן מובהק את אחוז המשתמשים שיחשפו למוצר. 

-- Step 1: create a simulated data table in BigQuery (runs once, result saved/stable)
-- Control is calibrated exactly to the real rate measured in GA4 (19.8%); Treatment simulates
-- a hypothetical improvement (~+18%) from the carousel design. Everything is documented in the table's OPTIONS(description=...).
CREATE OR REPLACE TABLE `keren-profile-website.experiments.landing_carousel_test` (
  user_pseudo_id      STRING,
  experiment_variant  STRING,   -- 'control' | 'treatment'
  assignment_ts       TIMESTAMP,
  viewed_item         BOOL      -- התוצאה שנמדדה: האם המבקר צפה במוצר
)
OPTIONS (description = "SIMULATED A/B test data. NOT real GA4 export data. " ||
  "Control probability = 0.198, the REAL first_visit->view_item rate (Case 01). " ||
  "Treatment probability = 0.2336, a hypothetical +18% lift. Generated by Claude.")
AS
WITH control AS (
  SELECT
    CONCAT('sim_ctrl_', LPAD(CAST(row_num AS STRING), 6, '0')) AS user_pseudo_id,
    'control' AS experiment_variant,
    TIMESTAMP_ADD(TIMESTAMP('2020-11-01 00:00:00 UTC'), INTERVAL CAST(RAND()*1209600 AS INT64) SECOND) AS assignment_ts,
    RAND() < 0.198 AS viewed_item
  FROM UNNEST(GENERATE_ARRAY(1, 19500)) AS row_num
),
treatment AS (
  SELECT
    CONCAT('sim_trt_', LPAD(CAST(row_num AS STRING), 6, '0')) AS user_pseudo_id,
    'treatment' AS experiment_variant,
    TIMESTAMP_ADD(TIMESTAMP('2020-11-01 00:00:00 UTC'), INTERVAL CAST(RAND()*1209600 AS INT64) SECOND) AS assignment_ts,
    RAND() < 0.2336 AS viewed_item
  FROM UNNEST(GENERATE_ARRAY(1, 19500)) AS row_num
)
SELECT * FROM control UNION ALL SELECT * FROM treatment;

-- שלב 2: ניתוח התוצאה - שאילתה אמיתית ורצה בפועל מול הטבלה שנוצרה
SELECT
  experiment_variant,
  COUNT(*)                          AS users,
  COUNTIF(viewed_item)               AS viewed_product,
  ROUND(COUNTIF(viewed_item) / COUNT(*), 4) AS view_item_rate
FROM `keren-profile-website.experiments.landing_carousel_test`
GROUP BY experiment_variant
ORDER BY experiment_variant DESC;

איך המדד חושב

שימוש ב-Two-Proportion Z-Test להשוואת שיעור ה-view_item בין שתי קבוצות בלתי תלויות. Pooled Proportion = 0.2122, SE = 0.00414, z = 8.64, p < 0.0001.

Lift = (Rate Treatment − Rate Control) / Rate Control = (23.01% − 19.43%) / 19.43% = +18.4%.

הנחות ובדיקות מקדימות

  • גודל מדגם מינימלי חושב מראש (Power Analysis) לזיהוי Lift של ~18% ברמת ביטחון 95% וכוח 80% - נדרשים כ-2,045 משתמשים לקבוצה;
    הריצה בוצעה עם 19,500 משתמשים לקבוצה, מרווח ביטחון נוח
  • קבוצת ה-Control מכוילת בדיוק לשיעור האמיתי שנמדד ב-GA4 Export (מקרה 01); קבוצת ה-Treatment מייצגת סימולציה של השערת המוצר, ולא תוצאות מניסוי בפועל.
  • בדיקת SRM (Sample Ratio Mismatch): החלוקה 50/50 מובנית מראש בטבלה משום שמדובר בנתונים מדומים - בניסוי חי יש לוודא זאת בפועל על ספירות אמיתיות

מסקנה עסקית

ההדמיה - המבוססת על ה-Control האמיתי (19.8%~) - מראה שקרוסלת מוצרים בעמוד הנחיתה עשויה להעלות את שיעור הצפייה במוצר בכ-18%.

המלצה
הרחבה מלאה של הקרוסלה על כלל המשתמשים ומעקב אחר המרות סופיות
  • החלטת מוצר (Full Rollout): מומלץ להחיל את קרוסלת המוצרים המומלצים על 100% מהמבקרים החדשים בעמוד הנחיתה, וזאת לאור תוצאות ה-A/B Test שהציגו עלייה מובהקת סטטיסטית של 18.4%+ בשיעור הצפייה במוצרים (p < 0.0001).
  • מעקב אחר המרות סופיות (Downstream Metrics): לבחון האם הגידול ב-view_item מתורגם באופן ישיר לעלייה במדדי ה-Downstream (המרות סופיות), בפרט שיעורי ההוספה לסל (add_to_cart) והרכישות בפועל (purchase).
03 · RETENTION

ניתוח שימור ו-Cohort לפי חודש הצטרפות

Cohort AnalysisBigQuerySimulated data

ניהול המוצר רצה להבין אילו קבוצות משתמשים (cohorts) שנרשמו בחודשים שונים נשארות פעילות זמן רב יותר, כדי לבחון האם שינויי מוצר או קמפיינים שבוצעו בחודש מסוים השפיעו בפועל על השימור לאורך זמן - ולא רק על מספר ההרשמות הגולמי. 

WITH user_cohort AS (
  -- כל משתמש משויך לחודש הקלנדרי של הפעילות הראשונה שלו
  SELECT
    user_id,
    DATE_TRUNC(MIN(event_date), MONTH) AS cohort_month
  FROM `project.analytics.sessions`
  GROUP BY user_id
),

user_activity AS (
  -- כל צירוף (משתמש, חודש) שבו הייתה לפחות פעילות אחת
  SELECT DISTINCT
    user_id,
    DATE_TRUNC(event_date, MONTH) AS activity_month
  FROM `project.analytics.sessions`
),

cohort_activity AS (
  -- months_since_signup = כמה חודשים חלפו מאז ההצטרפות ועד הפעילות הזו
  SELECT
    c.cohort_month,
    DATE_DIFF(a.activity_month, c.cohort_month, MONTH) AS months_since_signup,
    a.user_id
  FROM user_activity a
  JOIN user_cohort c USING (user_id)
),

cohort_size AS (
  -- גודל כל cohort, לצורך חישוב אחוזי שימור
  SELECT cohort_month, COUNT(DISTINCT user_id) AS cohort_users
  FROM user_cohort
  GROUP BY cohort_month
)

SELECT
  ca.cohort_month,
  ca.months_since_signup,
  COUNT(DISTINCT ca.user_id)                          AS active_users,
  cs.cohort_users,
  ROUND(COUNT(DISTINCT ca.user_id) / cs.cohort_users, 3) AS retention_rate
FROM cohort_activity ca
JOIN cohort_size cs USING (cohort_month)
GROUP BY 1, 2, cs.cohort_users
ORDER BY 1, 2;

איך המדד חושב

שימור בחודש N = מספר המשתמשים הייחודיים מתוך ה-cohort שהיו פעילים בחודש הקלנדרי ה-N ביחס להרשמה, חלקי גודל ה-cohort המקורי.

"פעילות" הוגדרה כאירוע session_start בודד לפחות באותו חודש - לא נדרשת פעילות רציפה בין החודשים.

הנחות עבודה

  • Cohort מוגדר לפי חודש הפעילות הראשונה, לא לפי תאריך יצירת החשבון
  • Cohorts שטרם הגיעו לגיל N חודשים מוצגים כ-N/A ולא כ-0%, כדי לא להטות את הממוצע
  • הושוו רק cohorts עם גודל מדגם דומה (10K–14K משתמשים)

מסקנה עסקית

ה-cohort שהצטרף במרץ 2026 שומר על שימור גבוה משמעותית לעומת ה-cohorts השכנים (ינואר-פברואר) בכל אחד מהחודשים שנמדדו.

המלצה

התאריך חופף להשקת עיצוב Onboarding מחודש בתחילת מרץ. מומלץ לבצע ניתוח סיבתי (או A/B ריטרואקטיבי) כדי לאשר קשר סיבתי, ואם מאושר - לשקול backport של הרכיב לזרם המשתמשים הוותיקים.

04 · MARKETING

דשבורד KPI שיווקי - CTR · CPA · ROAS

KPI TrackingBigQuerySimulated data

צוות השיווק רצה מעקב שוטף אחר ביצועי קמפיינים בערוצי מדיה שונים כדי להחליט היכן להזיז תקציב - תוך מעקב עקבי אחרי CTR, CPA ו-ROAS לאורך זמן ולא רק בנקודת זמן בודדת. 

WITH campaign_daily AS (
  -- אגרגציה יומית של ביצועי קמפיין לפי ערוץ
  SELECT
    date,
    channel,
    SUM(impressions) AS impressions,
    SUM(clicks)      AS clicks,
    SUM(spend)        AS spend,
    SUM(conversions) AS conversions,
    SUM(revenue)      AS revenue
  FROM `project.marketing.campaign_performance`
  GROUP BY date, channel
),

campaign_metrics AS (
  -- חישוב מדדי היעילות המרכזיים; SAFE_DIVIDE מונע חלוקה באפס
  SELECT
    date,
    channel,
    spend,
    revenue,
    SAFE_DIVIDE(clicks, impressions)   AS ctr,
    SAFE_DIVIDE(spend, conversions)    AS cpa,
    SAFE_DIVIDE(revenue, spend)        AS roas
  FROM campaign_daily
)

SELECT
  date,
  channel,
  ROUND(ctr, 4)   AS ctr,
  ROUND(cpa, 2)   AS cpa,
  ROUND(roas, 2)  AS roas,
  spend,
  revenue
FROM campaign_metrics
ORDER BY date, channel;

איך המדד חושב

CTR = קליקים / חשיפות. CPA = תקציב / המרות. ROAS = הכנסה / תקציב. כל המדדים חושבו הן ברמה יומית והן באגרגציה חודשית לצורך המגמה בדשבורד.

הנחות עבודה

  • הכנסה מיוחסת לערוץ לפי מודל Last-Click Attribution בחלון של 7 ימים
  • SAFE_DIVIDE משמש לכל היחסים כדי למנוע שגיאות בימים ללא נתונים
  • ROAS "משוקלל" (Blended) מחושב כהכנסה כוללת חלקי תקציב כולל, לא כממוצע פשוט בין ערוצים

מסקנה עסקית

ל-Display ROAS של כ-1.0x - כמעט גבול הרווחיות - בעוד ש-Paid Search שומר על ROAS יציב ועולה של מעל 4x לאורך כל התקופה.

המלצה

להסיט כ-30% מתקציב ה-Display ל-Paid Search, ולבחון את קריאייטיב ה-Display בנפרד לפני הכנסת תקציב נוסף לערוץ.
